## 緊急重設：救援 Email 上線前

第 3 階段（2FA）上線後，最高權限管理者若在第 10 階段前遺失驗證器將無法自救。
原規劃為「本機 CLI 緊急指令」，但 InfinityFree 沒有命令列環境，因此改為透過主機控制台的 phpMyAdmin 執行一段 SQL，
步驟見 [07-deployment.md](07-deployment.md) 第 3 節。

## 首次安裝流程（已實作）

InfinityFree 無 SSH，因此以網頁 `/install` 安裝：

1. `config/config.php` 不存在或不完整時，顯示設定說明頁（並提供可複製的隨機 `app_key`、`install_token`）；
2. 必須輸入 `config.php` 中的 `install_token`，避免網站剛上線時被陌生人搶先建立管理者；
3. 建立資料表（執行 `database/migrations/`）與第一位最高權限管理者，強制登入後綁定 2FA；
4. 資料庫已有使用者時一律拒絕，**不覆蓋、不刪除任何資料**；
5. 完成後寫入 `storage/installed.lock`，安裝頁永久回應 404。

後續 Schema 變更透過 `database/migrations/` 依序執行，由最高權限管理者在後台觸發，只允許「新增」型遷移；
任何會刪除或改變既有資料的遷移，必須先提出並取得同意。

## 階段 3 報告：使用者登入及 2FA（2026-10-30）

### 完成內容

| 功能 | 說明 |
|---|---|
| 登入狀態機 | 未登入 → 密碼正確 → 待驗證碼／強制綁定 → 完整登入；未完成前其他頁面導回對應步驟、API 回 401／403 |
| TOTP | 自行實作 RFC 6238，與 Google Authenticator 相容；時間容許範圍可設定；同一組驗證碼不能重複使用（條件式 UPDATE 保證併發下只成功一次） |
| QR Code | 伺服器端產生 SVG，不呼叫外部服務；附手動輸入金鑰 |
| 2FA Secret 保存 | 以 `app_key` 衍生的子金鑰（libsodium secretbox）加密後存入資料庫 |
| 強制綁定 | 新帳號、被管理者重設 2FA 的帳號，密碼正確後只能進入綁定頁 |
| 個人帳號設定 | 查看 2FA 狀態；修改密碼（需目前密碼）；更換驗證器（需目前密碼 + 目前驗證碼 → 掃描新 QR → 新驗證碼確認才替換） |
| Session 安全 | HttpOnly、SameSite=Lax、HTTPS 時 Secure；登入各階段更換 Session ID；閒置與絕對逾時；Session 檔存於專案 storage |
| 立即失效 | 每個請求重新讀取使用者；停用帳號、修改密碼、更換或重設 2FA 時其他裝置立即登出 |
| 登入節流 | 依帳號（HMAC 雜湊，不存原文）與 IP 計算；密碼與驗證碼錯誤合併計算；只有完整登入成功才重置 |
| CSRF | 所有 POST 檢查同步 Token |
| 安全標頭 | CSP（禁止 inline script）、X-Frame-Options、nosniff、Referrer-Policy、HTTPS 時 HSTS、`Cache-Control: no-store` |
| 歷史操作紀錄 | 登入成功／失敗、登出、2FA 綁定、更換 2FA、修改密碼、安裝；不含任何機密 |
| 安裝流程與部署包 | `/install`、`tools/build-deploy.php` 產生可「Upload & Unzip」的 zip |

### 測試結果

執行 `php tests/run.php`（MariaDB 10.11、PHP 8.3）：

- 單元測試 10 項全部通過：RFC 6238 測試向量、時間容許範圍、防重放、Base32、加密與竄改偵測、密碼規則、設定驗證、遷移檔拆分；
- 整合測試 27 項全部通過（實際啟動網站、以 HTTP 操作）：安裝金鑰與 CSRF、安裝後停用、未登入／未綁定時的頁面與 API 阻擋、
  Session ID 更換、帳號列舉防護、QR Code 不外送、綁定與登入、防重放、帳號鎖定、
  「已知密碼反覆猜驗證碼」不會重置鎖定、修改密碼使其他裝置失效、更換 2FA 舊驗證器失效、停用帳號立即登出、
  管理者重設 2FA 後強制重新綁定、紀錄不含機密、節流表不存帳號原文、IP 鎖定；
- Schema 驗證測試 26 項全部通過；
- 連續執行 3 次結果一致；
- Playwright 截圖檢查 375px 手機與 1280px 桌機版面，手機無水平捲動；
- 部署包（142 個檔案、約 196 KB）在 Apache 2.4 上實測：私有目錄全部被拒絕存取，安裝與登入流程正常。

### 開發中發現並修正的問題

- 遷移檔拆分使用 `\R` 時，非 UTF-8 模式下會把中文字中的 `0x85` 位元組當成換行，導致 SQL 被切壞；已改為只以 `\n`／`\r` 切割並加上單元測試。
- 設計節流時發現：若「密碼正確」就重置失敗次數，已知密碼的攻擊者可以無限猜驗證碼；已改為只有完整登入成功才重置，並加入整合測試。

### 已知限制

- 開發環境為 PHP 8.3，正式主機為 PHP 8.4；程式未使用 8.4 已淘汰的語法，但仍需在主機上實際操作確認；
- `.htaccess` 的存取保護已在開發環境的 Apache 2.4 驗證通過，但仍需在 InfinityFree 上依 07 文件第 4 節再檢查一次；
- 管理者重設員工 2FA、停用帳號的**介面**屬於階段 4，本階段以資料庫操作驗證其效果；
- Email 救援屬於階段 10；在此之前的緊急處理方式見 07 文件第 3 節；
- 登入失敗以外的紀錄查詢介面屬於階段 8，本階段紀錄已寫入資料庫。

## 階段 10 報告：最高權限管理者 Email 救援（2026-11-02，v0.10.0）

### 完成內容

| 項目 | 說明 |
|---|---|
| 入口 | 登入頁「最高權限管理者救援」→ `/recovery`；輸入帳號或救援 Email，選擇情境：忘記密碼（驗證器仍在）、遺失驗證器（記得密碼）、兩者都遺失 |
| 申請 | 只對「啟用中的最高權限管理者、帳號或 Email 相符、已設定寄信」寄信；所有情況畫面回應相同（決議 #34）；同一帳號每小時 3 次、同一 IP 9 次 |
| Token | `random_bytes(32)` 的 base64url 放在連結，資料庫只存 SHA-256；有效 30 分鐘（可設定）；同用途重新申請時舊連結失效；寄送失敗的連結立即作廢 |
| 確認頁 | GET 只顯示表單、不改任何狀態（郵件掃描器開啟連結不會完成救援）；`Referrer-Policy: no-referrer`、不快取 |
| 額外驗證 | 忘記密碼：輸入目前驗證碼（防重放）＋新密碼；遺失驗證器：輸入目前密碼；兩者都遺失：只有 Email，連結需等待冷卻時間（預設 30 分鐘）後才能使用。錯誤計入登入失敗鎖定 |
| 完成 | 單一交易：原子性 UPDATE 使用 Token（影響 1 列才繼續）→ 重設密碼／清除 2FA → `auth_version+1` → 其他未使用 Token 全部失效。不建立登入狀態，導回登入頁；寄送「救援已完成」通知 |
| 帳號設定 | 最高權限管理者的「Email 救援設定」：變更救援 Email（每次都要驗證碼、通知新舊 Email、舊連結失效）；列出待處理的救援申請並可取消；未設定寄信時提醒 |
| 系統設定 | 新增「Email 救援」分類：連結有效時間、兩者皆遺失的等待時間、每小時申請上限 |
| 紀錄 | `recovery.request`、`recovery.complete`、`recovery.cancel`、`recovery.email_change`（類別：安全），不含 Token、密碼、驗證碼與申請時輸入的原文 |

### 測試結果

`php tests/run.php`：單元 15、整合 146（含**救援 11** 項）全部通過。涵蓋：不存在的帳號、一般員工、未設定寄信時回應相同且不寄信；Email 不分大小寫；資料庫不存 Token 明文；GET 兩次不改狀態並帶 no-referrer；驗證碼錯誤、密碼太短不變更；成功後舊密碼失效、原登入裝置被登出、寄出完成通知；同一連結不能重用；重新申請讓舊連結失效；過期與偽造連結無效並記錄；遺失驗證器流程與強制重新綁定；兩者皆遺失的冷卻（冷卻中 POST 也無效）；頻率限制；取消救援申請；變更救援 Email 需驗證碼、通知新舊信箱、紀錄只存遮蔽 Email；員工呼叫救援設定 API 回 404；紀錄不含 Token 與新密碼。

畫面：手機 375 px 無水平捲動、無 CSP 錯誤。

### 已知限制

- 救援連結的 Token 在網址中，主機的存取記錄（access log）可能留下；Token 只能用一次且 30 分鐘後失效，風險有限；
- 救援的安全性等同救援信箱的安全性：請使用開啟兩步驟驗證的信箱；
- 有人反覆申請可讓真正的管理者在一小時內申請不到（頻率限制的副作用）；可等一小時或改用 07 文件第 3 節的緊急程序；
- 寄不出信時（寄信設定錯誤、服務停用）無法使用 Email 救援，仍需緊急程序；
- 實際寄達（InfinityFree → Brevo）尚待正式環境測試。

### 升級既有部署

不需資料庫更新（`admin_recovery_tokens` 已在 0001 建立）。升級後請到「帳號設定 → Email 救援設定」確認救援 Email，並到「系統設定 → 寄信設定」寄送測試信。

## 階段 9 報告：系統設定中心（2026-11-02，v0.9.0）

### 完成內容

| 項目 | 說明 |
|---|---|
| 入口 | 管理後台「系統設定」分頁，分「一般設定／寄信設定／附件儲存位置」三頁；只有最高權限管理者可進入（其他人 404） |
| 一般設定 | 依 `SettingsRegistry` 自動產生欄位（系統、登入與安全、附件、歷史紀錄、搜尋），含 `security.single_session` 開關。伺服器端依型別與範圍驗證，任一欄位錯誤時全部不儲存；字串不允許換行（防止信件標頭注入）；與預設值相同時刪除覆寫列 |
| 變更紀錄 | 每次儲存寫入 `settings.update`，記錄修改前後的值；機密只記「已更新／已清除」 |
| 再驗證 | 所有儲存、測試、連結 Google、中斷連結都需要管理者 10 分鐘內的再驗證（決議 #30） |
| 機密設定 | 新資料表 `secret_settings`（遷移 0004）：以 app_key 衍生、每個鍵各自的子金鑰加密；畫面只顯示「已設定」，留空表示不變更，可勾選清除 |
| 寄信 | 寄信方式：不寄信／SMTP／Brevo HTTPS API（決議 #3）。SMTP 支援 STARTTLS、SSL、AUTH LOGIN，驗證伺服器憑證、逾時 15 秒；提供「測試連線」（只登入不寄信）與「寄送測試信」（寄到管理者自己的 Email），顯示伺服器對話紀錄（帳號密碼遮蔽）。信件為 UTF-8 純文字，中文標頭以 RFC 2047 編碼 |
| Google Drive | OAuth 授權碼流程（state 64 位隨機值、10 分鐘有效、只能用一次）；只要求 `drive.file`；建立專用資料夾，重新連結同一帳號時沿用；Access Token 快取並在失效（401）時自動換新；已有附件存在某帳號時拒絕改連其他帳號，且在建立資料夾前就檢查 |
| 附件儲存 | `FileStorage` 改為 `put()` 回傳檔案代號、`open()` 取得可輸出的檔案；Google Drive 檔案下載到 `storage/tmp` 暫存，輸出後（或請求結束時）立即刪除。每個附件記住 `storage_driver` 與 `storage_ref`，切換預設位置後舊檔仍從原處讀取。本機與 Google Drive 的容量上限分開計算 |
| 中斷連結 | 需確認；向 Google 撤銷授權並刪除本機 Token；雲端檔案不刪除；新附件改回本機；畫面提示用原帳號重新連結 |

### 測試結果

`php tests/run.php`：單元 15、整合 135（含**系統設定 17** 項）全部通過。外部服務以 `tests/Fakes/` 的假 Google OAuth／Drive、Brevo API 與假 SMTP 伺服器取代，不需連網。涵蓋：
- 非管理者 404；未再驗證不能儲存；任一欄位錯誤全部不存；換行注入被拒；新舊值寫入紀錄；改回預設值刪除覆寫；
- SMTP 密碼只存密文、不回顯、留空不變更；連線測試、測試信（中文主旨與內文編碼）、密碼錯誤顯示 535 並記錄失敗；Brevo API 寄送；紀錄與設定表都不含任何密碼或金鑰；
- 未連結不可選 Google Drive；偽造 state、重複使用 state、使用者取消、授權碼錯誤都不建立連線；授權網址只要求 drive.file；
- 附件上傳到雲端（隨機檔名、放在專用資料夾、主機不留副本與暫存檔）；下載內容一致；三種無權限組合都是 404；Token 失效自動換新；雲端空間已滿時員工只看到一般訊息、詳細原因寫入紀錄；切回本機後舊檔仍可讀；刪除附件同時刪除雲端原檔與預覽圖；
- 中斷連結後撤銷授權、雲端檔案保留但回 502；改連其他帳號被拒；用原帳號重新連結沿用原資料夾並恢復讀取。

畫面：桌機與手機（375 px）無水平捲動、無 CSP 錯誤。

### 已知限制

- Google OAuth 同意畫面為「測試中」時，Google 會讓授權在 7 天後失效，需改為「已發布」（`drive.file` 不需 Google 審查）；
- 每次開啟雲端附件都要從 Google 下載一次（預覽圖也是），比本機慢；一則隨手記圖片很多時載入較久；
- 刪除雲端附件時若 Google 暫時無法連線，資料庫仍會標記刪除，雲端可能留下無法被存取的孤兒檔案（只記錄伺服器日誌）；
- 已存放的附件不提供「本機 ↔ Google Drive」搬移工具；
- 寄信只在設定頁測試，實際用途（Email 救援、安全通知）在階段 10 實作；寄達率與垃圾郵件判定取決於寄信服務與網域的 SPF／DKIM 設定；
- 真實 Google 與 Brevo 服務尚未在 InfinityFree 上實測（見部署文件的驗收步驟）。
