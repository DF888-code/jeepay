# 04 權限模型與安全設計

## 1. 雙重授權規則

### 1.1 權限來源

| 層級 | 資料表 | 欄位 | 由誰設定 |
|---|---|---|---|
| 第一層：全域 | `user_global_permissions` | 查看、編輯、建立、刪除、管理使用者（互相獨立） | 最高權限管理者，於「使用者權限管理」逐一設定 |
| 第二層：專案 | `project_permissions` | 查看、編輯、刪除 | 最高權限管理者，於各專案的權限設定頁 |

程式中**不存在**「初階工程師」「高階工程師」「合夥人」等角色常數；職稱若需要顯示，只是 `users` 上的自由文字（目前規格未要求）。

### 1.2 判斷矩陣

| 動作 | 最高權限管理者 | 一般使用者需同時具備 |
|---|---|---|
| 看到專案（列表、搜尋、詳細頁、版本歷史、隨手記、匯出） | 允許 | 全域查看 ∧ 專案查看 |
| 編輯專案（名稱、說明、關鍵字、新增／修改隨手記） | 允許 | 全域查看 ∧ 專案查看 ∧ 全域編輯 ∧ 專案編輯 |
| 刪除專案（及刪除他人隨手記，見待確認） | 允許 | 全域查看 ∧ 專案查看 ∧ 全域刪除 ∧ 專案刪除 |
| 建立專案 | 允許 | 全域建立（無既存專案可授權） |
| 設定專案授權名單 | 允許 | 不允許（規格 4.2 指定由最高權限管理者設定） |
| 使用者管理、全域權限、系統設定、歷史操作紀錄 | 允許 | 不允許（`can_manage_users` 的授權範圍待確認） |

**設計說明：為什麼編輯／刪除也要求「查看」**
編輯頁面必須先顯示內容；若只有編輯而無查看，等於可以修改看不到的資料，與「預設拒絕」原則衝突。
管理介面勾選「編輯」或「刪除」時會自動勾選「查看」，取消「查看」時一併取消其他項，並提示管理者。此規則列入待確認清單，可依需求調整。

### 1.3 必須套用授權的入口（清單即測試案例）

- 頁面：專案詳細、專案說明編輯、版本歷史、隨手記列表／新增／修改／刪除、關鍵字管理；
- API：上述所有 JSON 端點；
- 搜尋：專案名稱、說明、關鍵字、隨手記，含結果數量與摘要；
- 匯出／下載；
- 「相關專案資訊」（例如搜尋結果中的符合隨手記提示）。

### 1.4 實作約束

1. `Authorizer` 是唯一判斷入口，Controller 不可自行寫權限 SQL；
2. 每次請求重新查詢資料庫，不快取授權結果（撤銷立即生效）；
3. 專案 ID 只作為「要查哪一筆」的參考，授權結果完全由資料庫決定；
4. 使用者 ID 只取自 Session，不接受請求參數；
5. 拒絕時回傳與「不存在」相同的 404，避免洩漏專案存在與否；
6. 每個新增端點都必須有「無權限」測試案例，否則不得合併（Code Review 檢查項）。

## 2. 登入與 2FA

### 2.1 登入狀態機

```
         ┌─────────────┐  密碼正確                 ┌───────────────┐  TOTP 正確  ┌────────┐
未登入 ──►│ 輸入帳密     ├─────────────────────────►│ 待 TOTP 驗證  ├────────────►│ 完整登入 │
         └─────────────┘                           └───────────────┘             └────────┘
                │ 密碼正確但 must_enroll_2fa=1
                ▼
         ┌─────────────────┐ 掃描 QR + 輸入正確驗證碼
         │ 強制綁定 2FA     ├──────────────────────────────────────────────────► 完整登入
         └─────────────────┘
          此狀態下只能存取綁定頁與登出，其他頁面與 API 一律拒絕
```

- 密碼驗證成功後立刻 `session_regenerate_id(true)`，完成 TOTP 後再 regenerate 一次；
- 「待 TOTP」狀態有效時間短（預設 5 分鐘），逾時需重新輸入密碼；
- 帳號不存在、密碼錯誤、帳號停用回應相同訊息，避免帳號列舉；
- 不提供備用驗證碼（依規格）。

### 2.2 TOTP

- RFC 6238：SHA-1、6 位數、30 秒；允許前後時間步容許範圍可設定（預設 ±1）；
- `totp_last_used_step` 記錄最後成功使用的時間步，同一組驗證碼不能使用第二次（防重放）；
- TOTP 錯誤次數納入登入節流；
- Secret 以伺服器金鑰（`config.php` 內 32 bytes）透過 libsodium `secretbox` 加密後存入資料庫；
- QR Code 於伺服器端產生 SVG 直接嵌入頁面，**不呼叫任何外部 QR API**，頁面設定 `Cache-Control: no-store`。

### 2.3 個人帳號設定

| 操作 | 驗證要求 |
|---|---|
| 修改密碼 | 目前密碼 + 新密碼兩次輸入；成功後 `auth_version+1`，其他裝置 Session 失效，本 Session 重新發行 |
| 查看 2FA 狀態 | 已登入即可 |
| 更換 2FA 驗證器 | 目前密碼 + **目前驗證器的驗證碼** → 產生新 Secret（暫存 `totp_pending_*`）→ 掃描 → 輸入**新驗證器**驗證碼 → 原子性替換；期間舊驗證器持續有效，失敗不影響登入 |
| 手機遺失 | 無法自行更換（沒有舊驗證碼），需走 2.4 管理者重設 |

### 2.4 員工遺失手機（管理者重設 2FA）

1. 管理者於使用者管理頁點「重設 2FA」，再次輸入**管理者自己的 TOTP** 確認（重要操作再驗證）；
2. 系統清除該員工 `totp_secret_enc`，設定 `must_enroll_2fa=1`、`auth_version+1`（該員工所有 Session 立即失效）；
3. 員工下次登入：密碼正確 → 強制綁定 → 驗證成功才進入系統；
4. 記錄 `admin.user_2fa_reset`（操作者、對象），不記錄任何 Secret。

## 3. 最高權限管理者 Email 救援

### 3.1 情境與用途識別

| 情境 | Token `purpose` | 救援頁額外要求 | 完成後 |
|---|---|---|---|
| 忘記密碼、仍有驗證器 | `reset_password` | 設定新密碼前先輸入**目前 TOTP** | 新密碼生效，需重新以密碼 + 2FA 登入 |
| 遺失驗證器、知道密碼 | `reset_2fa` | 輸入**目前密碼** | 清除 2FA，`must_enroll_2fa=1`，下次登入強制綁定 |
| 兩者皆遺失 | `reset_both` | 只有 Email（最弱情境）→ 額外冷卻時間（預設 30 分鐘後才能使用，可設定） | 設定新密碼並強制綁定 2FA |

救援完成**不建立登入 Session**，一律導回登入頁，從頭走密碼 + 2FA。

### 3.2 流程

```
救援申請頁（輸入帳號或 Email，回應一律「若資料正確，將寄出郵件」）
   │  只對 is_super_admin=1 且 Email 相符者發信；其他情況靜默略過，但寫入安全紀錄
   ▼
產生 Token：random_bytes(32)（256 bits）→ base64url 放入連結
            資料庫只存 SHA-256、purpose、expires_at（預設 30 分鐘）
            同用途舊 Token 設 invalidated_at
   ▼
信件連結 GET /recovery/confirm?token=...
   │  只顯示確認頁（不做任何狀態變更）→ 郵件掃描器開連結不會完成救援
   │  頁面設定 Referrer-Policy: no-referrer，避免 Token 透過 Referer 外洩
   ▼
使用者在頁面中輸入額外驗證資料並 POST（含 CSRF Token）
   ▼
交易：原子性 UPDATE 標記 used_at（影響 1 列才繼續）
      → 重設密碼／2FA → auth_version+1 → 其他未使用 Token 全部失效 → COMMIT
   ▼
導回登入頁；寄送「救援已完成」通知信到救援 Email
```

### 3.3 安全要點

- 申請頻率限制（同 IP、同帳號，可設定）；
- Token、密碼、驗證碼不寫入任何 Log、錯誤訊息或寄信失敗訊息；
- 寄信失敗時，對使用者顯示一般性錯誤，對管理紀錄只寫「寄送失敗（SMTP 錯誤代碼）」；
- 救援申請、成功、失敗（過期、已使用、用途不符、驗證錯誤）都寫入 `activity_logs`（category=`security`）；
- 救援 Email 只能由最高權限管理者在登入狀態下於「救援設定」修改，修改時需再次輸入 TOTP，並通知舊 Email。

## 4. 通用 Web 安全

| 威脅 | 對策 |
|---|---|
| SQL Injection | PDO 參數化、關閉模擬 prepare；動態欄位名只能來自程式內白名單 |
| XSS | 樣板輸出一律 `htmlspecialchars`；隨手記以純文字顯示（保留換行），不渲染 HTML；CSP `default-src 'self'`，不使用 inline script |
| CSRF | 每個 Session 的同步 Token，所有狀態變更請求檢查；JSON API 以 Header 傳遞；Cookie `SameSite=Lax` |
| Session 劫持／固定 | `HttpOnly`、`Secure`、`session.use_strict_mode=1`、登入時 regenerate、閒置逾時與絕對逾時（可設定） |
| 密碼保存 | `password_hash`（Argon2id，主機不支援時 bcrypt）；登入時 `password_needs_rehash` 自動升級 |
| 暴力破解 | `login_attempts` 依帳號與 IP 節流，失敗次數與鎖定時間可設定 |
| 點擊劫持 | `X-Frame-Options: DENY`、CSP `frame-ancestors 'none'` |
| 資訊洩漏 | 正式環境 `display_errors=Off`；錯誤頁只顯示追蹤代碼；Log 不含秘密 |
| 信任前端輸入 | 使用者 ID 取自 Session；專案 ID、版本號、權限值皆在伺服器端重新驗證 |
| CSV 匯出公式注入 | 以 `= + - @` 開頭的儲存格前加 `'` |

## 5. 機密資料存放

| 機密 | 存放位置 |
|---|---|
| 資料庫帳密、應用金鑰（加密 TOTP Secret 與 HMAC 用） | `config/config.php`（不進版控，`.htaccess` 拒絕存取） |
| SMTP 密碼／API Key | 優先 `config/config.php`；若需介面設定，以應用金鑰加密後存資料庫，介面不回顯 |
| TOTP Secret | 資料庫，加密後保存 |
| 救援 Token | 資料庫只存 SHA-256 |
| 密碼 | 資料庫只存雜湊 |

> 一般資料庫設定表不是秘密管理系統；若資料庫被整份匯出，未搭配 `config.php` 的金鑰仍無法解出 TOTP Secret 與 SMTP 密碼。

## 6. 權限測試清單（階段 4–7 必須全部自動化）

| # | 情境 | 預期 |
|---|---|---|
| 1 | 無全域權限、有專案權限 | 拒絕 |
| 2 | 有全域權限、無專案權限 | 拒絕 |
| 3 | 兩者皆有 | 允許 |
| 4 | 兩者皆無 | 拒絕 |
| 5 | 權限撤銷後再次呼叫 API | 拒絕 |
| 6 | 直接修改 URL／API 中的專案 ID | 404 |
| 7 | 搜尋未授權專案的名稱／說明／關鍵字／隨手記 | 0 筆，且回應中無任何相關內容 |
| 8 | 直接開啟未授權專案網址 | 404 |
| 9 | 透過 API 讀取未授權的隨手記、版本歷史、匯出 | 404 |
| 10 | 2FA 尚未重新綁定時呼叫一般 API | 403 |
| 11 | 偽造 POST 中的作者 ID、使用者 ID | 被忽略，以 Session 為準 |
| 12 | 缺少或錯誤的 CSRF Token | 拒絕 |
| 13 | 帳號停用後使用舊 Session | 立即登出 |

Schema 層級的 1–6、7 已在 `tests/schema_smoke_test.php` 以真實 SQL 驗證；應用層測試將在對應階段補齊。
